The problem
The command centre’s dashboard only raised alarms. Checking, escalating and fixing every alert happened by hand, over WhatsApp and a shared sheet.
What I designed
A new dashboard built with object-oriented UX: the live map as home, one-click device reports, alerts, tickets and messages inside the system.
Where it landed
93.8% less information to hold in mind to read the system (2,467 → 152 bits), and a working coded prototype.

What we found

The dashboard raised the alarm. Everything after it happened by hand.

Too many alerts to check
5 of 6 operators said checking alerts by hand in busy periods wears them out, and real faults get missed.
Each check takes minutes
Operators cross-check device status, logs and camera feeds by hand: 3-7 minutes per alert.
WhatsApp is the workflow
All 6 said dispatch, updates and emergencies run over WhatsApp and phone calls, so nothing is on record.
No one sees where a repair is
Supervisors and managers track tasks by calling around or by updating a shared master sheet.
Repeat failures go unnoticed
4 of 6 said a device that keeps failing raises a fresh alert each time, with no history attached.
There is no map
To find where an alert is, operators memorise device IDs and look them up in lists of IP addresses.

Where one alert slows down

We mapped one alert across all seven roles, from the device raising it to the repair, and marked where it breaks down.

  1. The AI analytics can miss events it was never trained on.
  2. Checking an alert is entirely manual.
  3. Engineers have no trend analysis to work from.
  4. Dispatch runs over calls, WhatsApp and email.
  5. Logs are updated by hand, through mail and WhatsApp.
  6. So the repair itself waits on slow, unreliable messages.

Focus

We designed for the one workflow everything depends on.

An alert, from the moment a device raises it to the moment it is closed.

  1. DetectA camera, sensor or meter raises an alert.
  2. CheckThe operator confirms the alert is real.
  3. EscalateAn engineer finds the cause; serious cases go up.
  4. FixA field team repairs it on site.
  5. CloseThe record is updated and the alert closed.

Object-oriented UX

We designed around things, not pages.

Object-oriented UX starts from the things people work with, like alerts, devices and tickets, and what they do to them. Screens come last.

1. Every need becomes one sentence

We rewrote what each role told us as user stories, over a hundred of them across six roles. Each one names who acts, what they do, to what, and the detail that matters.

2. The first map was too big to use

Listing every object and action from those stories gave a grid of 140 objects by 77 actions. Only 400 of its 10,780 cells were used: the same few things, named many different ways.

3. Grouping cut it to 14 by 11

We merged everything that meant the same. ‘Camera down alert’, ‘fault alert’ and ‘alerts’ became one object, Alert. ‘Check’, ‘inspect’, ‘view’ and ‘supervise’ became one action, Monitor.

4. We measured what it saved

The dense map looked simpler, but “looks simpler” isn’t evidence. So we treated each map as information an operator has to read, and counted it in bits.

  1. Every cell is a yes or no.Each cell answers one question: does this action apply to this object? A map is a grid of these questions.
  2. Entropy says how much each cell tells you.Shannon entropy measures the information in a yes/no answer. If almost every cell is empty, each one tells you very little, but you still have to read them all.
  3. Cells × entropy = the whole map.Multiply the information per cell by the number of cells to get the total an operator has to take in.

H = −[ p log2 p + (1 − p) log2(1 − p) ]

p = the share of cells that are marked  ·  H = bits per cell  ·  total = cells × H

1 − 152 ÷ 2,467 = 93.8% less to read: the dense map is 6.2% of the original load. Each of its cells is close to the most informative a yes/no can be (1 bit), and there are 70 times fewer of them.

5. Every object gets its attributes

Before any screen, we wrote down the information that lives inside each of the seven core objects the dense map left us with (Alert, Device, Fault, Ticket, Field task, Infrastructure and Report): their sub-objects, and the fields that describe them. An Alert Item, for example:

  • Alert type
  • Severity
  • Alert status
  • Location
  • Zone
  • Issue description
  • Failure count
  • Last updated
  • Assigned to
  • Assigned role

This is what lets a screen be justified field by field: an operator monitoring an alert needs its severity, status and location, so those are exactly what an alert card shows.

6. Object + action = a task

Pairing each object with the actions that apply to it gave the real tasks people do in the system. The ones on our chosen workflow became the task list we ranked next.

  • Alert+Monitor=Monitor alerts
  • Alert+Escalate=Escalate an alert
  • Device+Analyse=Analyse a device
  • Fault+Repair=Repair a fault
  • Incident+Coordinate=Coordinate an incident
  • Ticket+Track=Check a ticket

The new dashboard

Each screen shortens one step.

Light mode for better visibility, one typeface, and one purple for everything you can act on.

The live map is the home screen

Devices coloured by status, crowded areas folded into numbered clusters, one filter bar.

Why: monitoring alerts is the most critical task, so the map never needs a click: every alert stays pinned on it.

One click opens the device

Acknowledge or ignore from the card. The full report adds the event log and a progress timeline.

Why: analysing an alert needs context, so the cause, the log and the affected industries sit in one view.

Every alert beside the map

A side panel lists the active alerts, and an AI overview flags devices that keep failing, with a likely cause and fix.

Why: this answers the repeat failures nobody was noticing, without leaving the map.

Alerts, in three tabs

A summary by domain, the full list, and escalation. The live counts stay pinned across all three.

Tickets for the field supervisor

Pick a ticket, pick an agent, and it is assigned. The engineer’s analysis is right there on the ticket.

Why: resolving field tasks is the supervisor’s most frequent job, so it gets a screen of its own.

Messages inside the dashboard

Threads linked to the device they are about, synced to field staff’s phones, and one broadcast for emergencies.

Why: this replaces WhatsApp, so every message becomes part of the incident’s record.

What I learnt

Name the things before drawing the screens.

Objects first
Defining Alert, Device, Fault and Ticket before any screen kept the dashboard to what really exists in the system.
Every field needs a reason
If a field can’t be traced to something a user needs, it comes off the screen.
Measure, don’t assume
Counting bits turned ‘this feels simpler’ into a number the team could defend.
